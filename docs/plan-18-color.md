# 계획 18 — 색 이론 조사와 사이트 전체 색 정리

날짜: 2026-10-08. 코드: `docs/tools/color-tokens.py`(생성·검사) → `site/assets/tokens.css`(자동 생성). 홈 `landing.css`, 서브페이지 `site.css`, `404.html`이 같은 토큰만 쓴다.

## 1. 조사한 원리와 이 사이트의 판단

출처는 블로그·튜토리얼 수준이라 수치는 지침으로만 쓴다. WCAG 조항 문구는 W3C 규범 문서를 직접 열어 확인하지 못했고 해설 자료([WebAIM](https://webaim.org/articles/contrast/), [W3C Understanding: Non-text Contrast](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast))에 기댔다.

| 원리 | 요지(출처) | 이 사이트의 판단 |
|---|---|---|
| 60-30-10 | 지배색은 중립, 보조색은 구조, 강조색은 희소해야 신호가 된다. 유연한 지침이지 공식이 아니다 ([Rometheme](https://rometheme.net/blog/uncategorized/the-60-30-10-color-rule-in-ui-design/)) | 홈 배경 면적을 쟀다: 종이 약 63% · 블루 13% · 구획 11% · 주황 12%. 종이가 지배색이고 주황은 문의 한 면에 몰려 희소성이 유지된다. 잉크(글자·선)는 별도 |
| 보색과 진동 | 보색 쌍은 대비가 강하지만 채도가 높고 명도가 비슷한 경계에서 색이 떨린다. 해법: 중립 완충선, 한쪽 채도·명도 조정, 보색은 작은 면에만 ([Tuts+ 진동 경계](https://design.tutsplus.com/articles/vibrating-boundaries-making-colors-pop--cms-108939), [LogRocket](https://blog.logrocket.com/ux-design/clashing-colors-ux-design/), [Inventive HQ](https://inventivehq.com/blog/color-harmonies-guide-web-design)) | 주황과 블루는 색상각 137° 차(OKLCH), 명도 차 0.17로 **보색에 가깝고 명도도 가깝다.** 그래서 ①둘이 맞닿지 않게 중간에 종이 구획을 둔다(관계 → 팀 → 문의 순서) ②색 면에는 잉크 3px 선을 둘러 완충한다 ③주황 글자를 블루 위에 얹지 않는다(대비 1.98:1) |
| 동시 대비 | 인접 색이 서로의 보색 성분을 끌어낸다 ([Tuts+](https://design.tutsplus.com/articles/simultaneous-contrast-make-your-colors-work-smarter--cms-108963)) | 흰 도형이 블루 위에서 더 밝아 보이는 효과는 그대로 쓰고(관계 섹션), 주황 면은 종이와 직접 맞대지 않고 잉크 선을 둔다 |
| 조화 유형 | 초보에게는 유사색·분할 보색이 안전, 보색은 강조에만 ([Inventive HQ](https://inventivehq.com/blog/color-harmonies-guide-web-design)) | 브랜드가 이미 정한 주황+블루(거의 보색)는 바꾸지 않는다. 대신 면적과 역할을 분리해 장력을 관리한다 |
| 접근성 대비 | 글자 4.5:1, 그래픽·UI 3:1, 색만으로 정보를 전달하지 않기(WCAG 1.4.3 / 1.4.11 / 1.4.1) | `color-tokens.py`가 17개 쌍을 계산한다. 아래 §3 |
| 톤 스케일 | OKLCH에서 색상·채도는 유지하고 명도만 고르게 나누면 균일한 램프가 된다. 색역을 벗어나면 채도를 줄여야 한다 ([DEV](https://dev.to/okabrionz/universal-oklch-color-system-blueprint-one-base-color-design-tokens-3639), [ColorBox](https://colorbox.io/oklch-color-palette-generator)). 명도는 "지각에 가깝지만 정확하지는 않다" | 브랜드 원값을 주황 500·블루 600에 고정하고 10단계를 파생. 쓰는 단계는 4개뿐(YAGNI) |

## 2. 점검에서 나온 문제와 수정 (이전 → 이후)

| # | 문제 | 수정 |
|---|---|---|
| 1 | **홈과 서브페이지가 서로 다른 색**을 썼다: 주황 `#FF5A1F` 대 `#FF6A00`, 블루 `#1E548C` 대 `#3659E3`, 잉크 `#151515` 대 `#1A1A1A` | `tokens.css` 하나로 통일. 로고 파일 실측값 채택(아래 §4 충돌) |
| 2 | 밝은 구획(`#EEECE5`) 위 주황 라벨이 **4.42:1**로 기준 미달(`#B84A00`) | `orange-700 #9A3D00`: 종이 6.38 · 구획 5.84 · 흰 6.90 |
| 3 | 서브페이지 블루 타일 위 **주황 글자**(진동·저대비) | 흰 글자로 교체 |
| 4 | 블루 위 비활성 도형을 흰색 투명도 .74로 표현(탁해짐) | 블루 톤 `blue-200` 단색 |
| 5 | 선택된 칩이 **색만으로** 구분됨(1.4.1) | 주황 채움 + ✓ 표시 |
| 6 | 블루·주황 전면 섹션에 경계선이 없음(보색 완충 부재) | 잉크 3px 위아래 선 |
| 7 | 호버·눌림 색이 CSS에 하드코딩된 hex | 토큰(`orange-400`, 잉크 혼합)으로 교체. CSS에 hex가 남지 않음 |
| 8 | 서브페이지 입력 포커스 링이 반투명 주황(대비 불명) | 잉크 외곽선 + 불투명 주황 링 |
| 9 | 404 페이지가 하드코딩 색과 **옛 Pages 경로(`/remo-web/`)**를 씀(Vercel에서 파비콘·홈 링크가 깨짐) | 토큰 사용, 경로를 `/`로 |
| 10 | 서브페이지 내비 라벨(WORK·PEOPLE·ABOUT)이 홈(한글)과 다름, 서브페이지 헤더에 배지 없음 | 홈과 같은 말·모양(배지, 하는 일 / 프로젝트 / 팀 / 문의 알약) |

서브페이지 외곽선 언어도 홈과 맞췄다(카드·폼·칩·사진 타일 3px 잉크, 둥근 28px).

## 4. 충돌과 한계

- **브랜드 가이드 v4의 블루와 다르다.** 가이드는 Ocean Blue `#1E548C`·주황 `#FA7000`(JPEG 실측, "벡터 원본으로 재확인 필요"로 표시됨)이고, 새 로고 파일(820px PNG)에서 실측한 값은 코발트 `#3659E3`·주황 `#FF6A00`이다. 후자가 무손실 파일이라 더 믿을 만하지만, **어느 블루가 공식인지는 팀이 확정해야 한다.** 확정이 가이드와 다르면 `color-tokens.py`의 `BRAND` 한 줄만 고치면 전체가 다시 계산된다. 가이드 문서 자체는 고치지 않았다.
- 색 비율은 배경 면적만 쟀다(글자·선 제외). 홈 하나, 데스크톱 폭 하나에서만 쟀다.
- 색각 이상 시뮬레이션은 모델 근사이고 실제 사용자 테스트가 아니다.
- 다크 모드는 정의하지 않았다.
- `site/lab/` 시안은 이 정리의 대상이 아니다(별도 하드코딩 색).
- 사진이 없는 팀 페이지 빈 타일은 그대로다(사진 대기).
- 실기기·다른 브라우저(특히 `color-mix()` 지원)와 인쇄는 확인하지 못했다. `color-mix`가 없으면 불투명 종이색으로 대체된다(선언 순서로 대비).
